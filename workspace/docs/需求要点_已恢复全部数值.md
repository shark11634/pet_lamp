## 1. 定义与范围

| 项 | 内容 |
|---|---|
| 产品 | 宠物活动状态灯（V1），版本号 **V1.0** |
| 一句话定义 | 家中一盏桌面氛围灯，**不依赖手机、互联网、云服务或智能家居中枢**，直接接收宠物佩戴端发送的活动状态数据，以柔和的颜色/亮度/呼吸效果显示宠物状态 |
| 核心体验 | 用户**不需要打开 App**，佩戴端也不必与手机连接。只要佩戴端与灯在有效蓝牙范围内、两者都供电，灯就自动展示宠物当前活动状态 |
| 非目标 | 不开发手机 App；不接入小米/涂鸦/HomeAssistant/Alexa/GoogleHome；不要求 Wi-Fi、互联网、云端账号或远程控制；不要求 GPS、宠物定位、围栏或离家提醒；不要求医学级运动/睡眠/健康分析；不要求多宠物、多灯群组联动（协议**应预留扩展空间**）；不在 V1 解决量产认证、外观开模、结构定制、长期电池寿命与完整安规 |

### 1.1 V1 默认状态表达（灯效表）

| 状态 | 灯光含义 | 色温 / 颜色 | 亮度 | 建议视觉效果 |
|---|---|---|---|---|
| `Quiet` | 宠物静止、睡眠或活动很少；设备在线 | **2400–2700 K 暖白** | **2 % – 8 %** | 常亮或约 **12 秒**的极慢呼吸 |
| `Light` | 走动、轻微玩耍或日常活动；设备在线 | 低饱和青绿 / 黄绿 | **8 % – 20 %** | **2–4 秒**柔和渐变 |
| `Active` | 跑跳、剧烈玩耍或高活动强度；设备在线 | 蓝青、天蓝或暖橙 | **20 % – 40 %** | **0.8–2 秒**渐变，**不允许高频闪烁** |
| `Lost` | 规定时间内未收到有效佩戴端广播 | 暗紫或暗琥珀 | **2 % – 6 %** | 每 **20–60 秒**一次慢呼吸 |
| `LowBattery` | 设备在线但电量低 | 保持当前活动状态色 | 当前亮度 | 每 **5–10 分钟**加入一次短暂、低亮度暖黄提示 |
| `Boot` | 灯端启动或正在开始扫描 | 柔和暖白 | — | 约 **1 秒**柔和暖白渐亮，再进入等待数据状态 |

## 2. 总体系统架构

```
┌──────────────────────────┐
│ 宠物佩戴端                │
│  IMU 加速度计             │
│  MCU + BLE               │
│  电池与电量检测            │
│  活动分类 / 心跳广播       │
└────────────┬─────────────┘
             │ BLE 广播（Advertising，建议每 1–2 秒）
             │ 无连接、无手机、无云
             ▼
┌──────────────────────────┐
│ 桌面灯端                  │
│  ESP32 BLE Scanner        │
│  协议解析、校验、去重      │
│  last_seen 失联判断        │
│  本地状态机                │
│  RGB + 白光 PWM 灯光引擎   │
└────────────┬─────────────┘
             ▼
      用户可见的柔光状态灯
```

### 2.1 最终运行原则

1. 佩戴端只需要 **BLE 广播**，不需要与灯保持 **GATT 长连接**。
2. 灯端应作为 **BLE Scanner / Observer**，持续监听来自已绑定佩戴端的广播。
3. 灯端判断失联的**唯一依据**：在设定时间内未收到有效广播包。
   **宠物不动不是失联**；宠物静止时佩戴端仍必须发送心跳广播。
4. 正常运行时不依赖手机、Wi-Fi、路由器、互联网、云服务或 HomeAssistant。

## 3. 灯端硬件路线（V1 已确定）

推荐以 **米家床头灯 2（Mijia Bedside Lamp 2，`bslamp2` / `MUE4093GL` 同系列）**
为完整灯体基础。理由：已有完整外壳、柔光灯罩、灯板、触控面板和外置 **12 V** 低压适配器；
RGB + 白光、低亮夜灯、桌面氛围灯外观已经成熟；内部为 **ESP-WROOM-32D**，已有公开逆向与
ESPHome 自定义固件项目；外置 12 VDC 适配器使首次串口烧录和调试**不需要接触灯具内的市电电源**。

备选路线：**Athom 12 W E27 ESPHome RGB CCT 灯泡 + 全包乳白/磨砂罩 E27 台灯**。
固件开放性更好，但灯泡为 **100–240 VAC** 市电产品，且需额外解决灯罩、结构与市电调试边界。

### 3.3 灯端状态机（4.3 节）

```
BOOT
 │ ├─ 上电暖白提示约 1 秒
 ▼
SCANNING / WAITING
 │ ├─ 收到并验证有效包 ─────────────┐
 │ │                                ▼
 │ │                    QUIET / LIGHT / ACTIVE
 │ │                                │
 │ └─ 超时未收到包 ───────────────► LOST
 └─ 收到有效包后平滑恢复到对应状态
```

失联判断规则：

| 从最后有效包开始的时间 | 建议行为 |
|---|---|
| **0–10 秒** | 保留最后一个状态；容忍短暂丢包 |
| **10–30 秒** | 可逐步降低当前状态亮度；**不立即报警** |
| **30–60 秒** | 进入 `Lost` 状态：低亮暗紫/暗琥珀慢呼吸 |
| **超过 5 分钟** | 保持 **1 %–3 %** `Lost` 灯效，或进入熄灯；以用户体验测试决定 |

**V1 默认 `lost_timeout_ms = 60,000`。该参数必须可编译配置，后续可通过本地维护接口配置。**

### 3.4 灯效参数（4.4 节）

| 状态 | RGB / 色温 | 亮度 | Transition | 动效 |
|---|---|---|---|---|
| `Quiet` | **2400–2700 K 暖白** | **2–8 %** | **4–8 秒** | 静止或 **12 秒**低幅度呼吸 |
| `Light` | 青绿 / 黄绿 | **8–20 %** | **2–4 秒** | 缓慢浮动，可选 |
| `Active` | 蓝青 / 天蓝 / 暖橙 | **20–40 %** | **0.8–2 秒** | 仅柔和变化，**禁止频闪** |
| `Lost` | 暗紫 / 暗琥珀 | **2–6 %** | **3–5 秒** | 每 **20–60 秒**一次慢呼吸 |
| `LowBattery` | 保持原状态色 | 当前亮度 | **0.5–1 秒** | 每 **5–10 分钟**一次低亮黄白提示 |

**避免事项：**

* 不做 **3 Hz** 以上的可见闪烁；
* 不在夜间把 `Active` 设为 **100 %** 高亮；
* 不把 `Lost` 设计成持续红色爆闪 —— 失联可能只是宠物走远、设备没电或灯刚断电重启；
* 不让每一个收到的广播都触发一次新动画；只在状态/强度发生显著变化时刷新目标值。

### 3.5 调光与 Gamma（4.5 节）

* 亮度由**线性逻辑亮度**换算成 **Gamma 校正后的 PWM 占空比**，建议初始 **`gamma = 2.2`**；
* 实测 **1 %–10 %** 亮度是否有可见跳变或抖动；如低亮不稳定，**提高最小稳定亮度**，
  而不是无限压低 PWM；
* RGB 与白光可分别采用不同的 Gamma 或最大通道系数；
* 需要**全通道限流**，避免 RGB + 白光同时满功率的热量与电流异常。

### 3.6 灯端 BLE 处理流程（4.6 节）

```
收到 BLE 广播
  ├─ 是否包含正确 CompanyID？      否则丢弃
  ├─ 长度是否为预期？              否则丢弃
  ├─ ProtocolVersion 是否支持？    否则丢弃
  ├─ DeviceID 是否等于已绑定 ID？  否则丢弃
  ├─ CRC 是否正确？                否则丢弃
  ├─ Sequence 是否为重复或过旧？   是则丢弃
  └─ 有效：
       更新 last_seen
       更新 battery / flags / activity_score
       根据 activity_state 更新目标灯效
       若此前为 LOST，执行恢复连接动画
```

**Sequence 规则：** 16-bit 无符号递增，最大值后回到 0，灯端**必须处理回绕**；
只接受比 `last_sequence` 更新的包；佩戴端重启时允许通过连续收到相同 `DeviceID` 的新包
重新同步，**连续 3 个合法包后放宽一次**序号判断。

### 3.7 灯端职责（4.1 节）

1. 持续被动扫描 BLE 广播；
2. 只接受已绑定佩戴端 `DeviceID` 的合法包；
3. 校验协议版本、包长度、CRC、序号；
4. 保存最后一次收到有效包的时间 `last_seen`；
5. 基于数据更新本地宠物状态机；
6. 对 RGB / 白光输出平滑、低闪烁的效果；
7. 在佩戴端失联、低电量、异常或恢复连接时提供**明确但不过度警报化**的视觉反馈；
8. 不依赖手机、互联网、云平台或 HomeAssistant。

## 4. 佩戴端需求

### 4.1 佩戴端职责（3.1 节）

1. 读取 IMU 运动数据；
2. 在本地把原始运动数据归类为安静、轻度活动、活跃等状态；
3. 读取剩余电量和可选的佩戴状态；
4. 以固定间隔 BLE 广播状态和心跳；
5. 在状态发生显著变化时**立即额外广播一次**；
6. 在低功耗条件下持续工作。

### 4.2 V1 推荐硬件（3.2 节）

| 模块 | 推荐 | 要求说明 |
|---|---|---|
| 无线 MCU | **Nordic nRF52840 / nRF52833 / nRF52832**；或 **ESP32-C3** 作为快速开发替代 | 量产优先 Nordic；快速验证可使用 ESP32-C3 |
| IMU | **三轴加速度计即可**；优先低功耗 | **6 轴 IMU**；V1 主要用加速度幅度与变化量，**不强制使用陀螺仪** |
| 电池 | 单节 **Li-Po**，建议 **100–300 mAh** | 最终容量按尺寸与续航目标定；V1 可先选开发板已有电池方案 |
| 充电 | Li-Po 线性充电 IC，USB-C 或磁吸触点 | V1 允许使用开发板原有充电方案 |
| 电量检测 | **ADC 分压或电量计 IC** | 需输出 **0–100 %** 或至少低电量标志 |
| 指示 / 按键 | 可选 | 用于配对、测试、充电状态；非 V1 必须 |
| 外壳 | 可先用硅胶套 / 3D 打印壳 | 首版先确保佩戴安全、圆角、无可吞咽小件 |

### 4.3 MCU 选择建议（3.3 节）

* **正式产品方向：Nordic nRF52 系列**。低功耗 BLE 广播和可穿戴设备生态成熟，
  适合电池供电、长续航与稳定广播。
* **快速原型方向：ESP32-C3**。开发门槛低、与灯端 ESP32 工具链相近、
  便于用 **ESP-IDF 或 Arduino** 快速做模拟佩戴端。
  但 ESP32-C3 **不应被默认视为最终续航最优选**。

### 4.4 运动状态定义（3.4 节）

**推荐计算量：**

1. 对每个加速度样本计算加速度向量模长；
2. 使用低通或滑动窗口估计**重力基线**，再计算**动态加速度**；
3. 每 **2–5 秒**窗口计算：**平均动态加速度**、**峰值动态加速度**、
   **超过活动阈值的样本比例**、可选**加速度变化率/方差**。

**建议初始分类规则：**

| 状态 | 进入条件 | 连续满足时间 |
|---|---|---|
| `Quiet` | 动态加速度均值低于 **`T_quiet`**，且峰值低 | **连续 10–20 秒** |
| `Light` | 超过低阈值但未达到高阈值 | **连续 3–5 秒** |
| `Active` | 均值、峰值或超阈值比例达到 **`T_active`** | **连续 2–3 秒** |
| 从 `Active` 降级 | 活跃指标下降 | **采用更长的退出时间**，避免频繁跳变 |

**防抖建议：** 初始阈值**不应写死在产品逻辑中**，应使用可配置常量，
并通过真实宠物测试校准。V1 的目标是"**观感上合理**"，不是精确测量消耗卡路里。

### 4.5 广播机制（3.5 节）

采用 **BLE Advertising**，而不是常连 GATT：佩戴端耗电更低；不需要配对、连接维持、
重连管理或手机参与；灯端上电即扫，天然适合检测"最后一次出现时间"。
后续可以扩展一只佩戴端对应多个灯，或一盏灯监测多个佩戴端。

| 场景 | 建议广播间隔 |
|---|---|
| V1 固定策略 | **1–2 秒** |
| 安静状态优化策略 | **3–5 秒** |
| Light / Active | **0.5–1 秒** |
| 状态改变时 | 立即发送 **1–3 个**冗余广播 |
| 低电量 | **仍保持心跳，不可直接停发** |

> V1 建议先固定为 **每 1 秒一次**，优先验证可靠性；电池优化放在后续阶段。

### 4.6 自定义 BLE 数据协议（3.6 节）

数据放在 **BLE Manufacturer Specific Data** 中。

| 偏移 | 字段 | 长度 | 示例 | 说明 |
|---|---|---|---|---|
| 0–1 | `CompanyID` | 2 bytes | `0xFFFF`（开发阶段） | 量产前申请或替换为自有分配值 |
| 2 | `ProtocolVersion` | 1 byte | `0x01` | 协议升级兼容 |
| 3–6 | `DeviceID` | 4 bytes | `0x12345678` | 每个佩戴端唯一；灯绑定此 ID |
| 7–8 | `Sequence` | 2 bytes | 递增 | 去重、防重放、发现卡死 |
| 9 | `ActivityState` | 1 byte | `0 / 1 / 2` | `0 Quiet`、`1 Light`、`2 Active` |
| 10 | `ActivityScore` | 1 byte | `0–255` | 细粒度活动强度 |
| 11 | `BatteryPercent` | 1 byte | `0–100` | 电量百分比 |
| 12 | `Flags` | 1 byte | bitfield | 佩戴、充电、故障、配对请求等 |
| 13 | `CRC-8` | 1 byte | 计算值 | 检测数据错误，**非安全认证** |
| | | | | **总长度：14 bytes** |

**Flags 定义：**

| Bit | 名称 | 含义 |
|---|---|---|
| 0 | `WORN` | 已检测到处于佩戴状态；V1 无佩戴检测可固定为 **1** |
| 1 | `CHARGING` | 正在充电 |
| 2 | `SENSOR_ERROR` | IMU / 电池检测异常 |
| 3 | `PAIR_REQUEST` | 设备希望请求绑定 |
| 4 | `LOW_BATTERY` | 电量低于阈值，例如 **20 %** |
| 5–7 | `Reserved` | 保留 |

**CRC 与安全说明：** CRC-8 用于检测广播数据损坏或误解析；**CRC 不能防止伪造包**。
V1 需要先保证稳定通信；若要防止附近设备伪造数据，**V1.1** 可增加**截断 HMAC**、
**滚动计数器**与**预共享密钥**。

> 📌 **本工程的落地约定**：需求文档"总长度 14 bytes"与"CompanyID 位于偏移 0–1"
> 两种口径不自洽。本工程固定采用 **Manufacturer Specific Data = 16 字节**
> （`CompanyID(2) + Payload(14)`，Payload 偏移 0–13），
> CRC-8 覆盖 **Payload 偏移 0–12**、校验字段在 **Payload 偏移 13**。
> 详见 [`protocol/README.md`](protocol/README.md) §2 与 §4。

### 4.7 佩戴端伪代码（3.7 节）

```
init IMU
init BLE advertising
init battery monitor
load DeviceID and sequence from NVS/flash
loop every 100 ms:
    read IMU
    update rolling activity window
loop every 1 s:
    classify activity: QUIET / LIGHT / ACTIVE
    read battery
    build advertising packet
    increment sequence
    advertise packet
    on activity state change: advertise packet immediately 1–3 times
    on battery below threshold: set LOW_BATTERY flag
    on sensor error: set SENSOR_ERROR flag
    continue heartbeat advertising whenever possible
```

### 4.8 佩戴端验收要求（3.8 节）

* 设备静止时仍**每 1–5 秒**发送一包心跳；
* **1–10 米**室内距离内，灯端可稳定收到广告；
* 状态由 `Quiet → Light → Active` 的更新时间**不超过 5 秒**；
* 停止广播后，灯端能按配置进入 `Lost` 状态；
* 电量变化可正确显示到广播包；
* 至少持续运行 **24 小时**，不发生广播完全停止、死机或序号不更新。

## 5. 灯端实操：刷机与开发

### 5.1 安全边界

* 灯体由外置 12 V 适配器供电，首次调试相对安全，但**仍要在断电后拆机、接线**；
* **不要使用 5 V TTL 串口模块；必须使用 3.3 V 逻辑电平**；
* **不要把 USB-TTL 的 VCC 接到灯电源线路**；
* 灯使用**原装 12 V 适配器**供电；USB-TTL 只接 **TX、RX、GND**；
* 首次覆盖固件前**必须完整备份原厂 Flash**；
* 推荐采购**两台灯**：一台原厂对照，一台用于刷机。

### 5.2 所需工具

米家床头灯 2（`bslamp2` / `MUE4093GL` 同系列），建议 **2 台**；
USB-TTL（**CP2102、CH340、FT232**，3.3 V 逻辑）；跳线 **TX、RX、GND、GPIO0** 至少 **4 根**；
小十字螺丝刀（拆底盖）；万用表（推荐，确认共地和接线）；电脑（Windows / macOS / Linux）；
原装 **12 V** 适配器为灯供电；可选 ESP32 / nRF52 开发板模拟佩戴端 BLE 广播。

### 5.3 打开灯体

1. 拔掉灯的 12 V 适配器；
2. 将灯翻转，取下底部橡胶脚垫；
3. 拧下脚垫下方隐藏的 **4 颗**螺丝；
4. 小心拆下底盖，拍照记录 PCB、线束和版本信息；
5. 在 PCB 上寻找 **TX、RX、GND、GPIO0** 调试焊盘。

### 5.4 串口接线

```
USB-TTL          灯端 PCB
TX      ───────► RX
RX      ◄─────── TX
GND     ──────── GND
跳线 GPIO0 ↔ GND ；仅进入下载模式时使用
```

### 5.5 进入下载模式

1. 灯断电；
2. TX、RX、GND 接好；
3. **GPIO0 与 GND 短接**；
4. 接上 12 V 适配器；
5. 约 **1–2 秒**后可开始执行烧录工具连接命令；
6. 成功进入下载模式后可移除 GPIO0-GND 短接。

### 5.6 读取芯片与备份 Flash

```bash
# 安装工具
python -m pip install esptool

# 检查连接（端口名按电脑实际情况替换）
esptool.py --chip esp32 --port COM3 --baud 115200 chip_id

# 完整读取原厂 4MB Flash
esptool.py --chip esp32 --port COM3 --baud 115200 \
  read_flash 0x000000 0x400000 bedside-lamp2-original-4mb.bin
```

**要求：** 确认文件大小**约为 4 MB**；在**至少两个安全位置**保存；
**不要公开上传该镜像**，其中可能包含设备标识或网络配置。

### 5.7 中间验证固件

仓库：**`https://github.com/mmakaay/esphome-xiaomi_bslamp2`**

目标：确认 **RGB、白光、触控、亮度滑条、面板指示灯和 OTA** 都正常。
ESPHome **仅用于过渡验证**；最终**不以 HomeAssistant 为运行前提**。

项目已有针对 `bslamp2` 的硬件支持、**单核 ESP32 设置**、
**eFuse MAC CRC 兼容处理**、灯光驱动和触摸面板实现。

### 5.8 bslamp2 构建注意事项

该灯内部 ESP32 有**特殊兼容要求**，ESP-IDF / ESPHome 构建必须处理：

```
CONFIG_FREERTOS_UNICORE=y        # 必须单核
ignore_efuse_custom_mac = true   # ESPHome 侧开关
ignore_efuse_mac_crc    = true   # ESPHome 侧开关
```

以项目最新的 `example.yaml` 和文档为准；**不要仅套用普通 ESP32 DevKit 的默认模板**。

### 5.9 刷写原则

* 先按开源项目生成的**完整安装命令和 offset** 刷写；
* 如编译输出包含 **`bootloader`、`partition table`、`app`** 多个文件，
  **必须全部按正确 offset 写入**；
* **不要随意把单一 `firmware.bin` 写入未知地址**；
* 初次使用 **115200 baud**，稳定后再提高；
* 烧录后移除 GPIO0-GND、断电重启，并通过 **115200** 串口日志确认启动。

### 5.10 失败恢复

1. 检查 12 V 供电、GND、TX/RX 是否接反、GPIO0 是否正确；
2. 再次进入下载模式，执行 `chip_id` 确认 Bootloader 可见；
3. 检查是否遗漏单核或 eFuse MAC CRC 兼容配置；
4. 使用原厂备份恢复：

```bash
esptool.py --chip esp32 --port COM3 --baud 115200 \
  write_flash -z 0x000000 bedside-lamp2-original-4mb.bin
```

5. 断电、移除 GPIO0-GND、重新上电，验证原厂状态恢复。

| NVS 写入 | **仅绑定、设置改变时；不要每包写 Flash** |

## 7. 绑定、维护与用户交互

### 7.1 V1 最简绑定（7.1 节）

**V1 可以允许工程师在编译时写死 `BOUND_DEVICE_ID`，快速验证整个方案：**

```c
#define BOUND_DEVICE_ID 0x12345678
```

### 7.2 V1 建议的现场绑定方式（无 App）

1. 灯处于正常状态时**长按电源/模式键约 5 秒**；
2. 灯以低亮蓝白呼吸表示"等待绑定"，持续 **60 秒**；
3. 佩戴端在 **60 秒内**把 **`PAIR_REQUEST` 位置 1** 并以 **0.5–1 秒**间隔广播；
4. 灯识别第一个合法协议包后，用白色闪烁一次或常亮 **2 秒**确认；
5. 灯将 `DeviceID` 写入 **NVS**；
6. 灯退出配对模式，进入正常监听。

> **注意：** V1 配对模式**不应自动接受附近任何 BLE 设备**；
> 至少要求符合 `CompanyID`、协议版本、`CRC` 和 `PairRequest` 格式。

### 7.3 手动控制优先级

1. **长按**：进入/退出配对或维护模式；
2. **短按**：临时熄灯或恢复自动显示；
3. **滑条**：只影响全局亮度上限，**不改变活动状态颜色规则**；
4. **自动状态**：除非用户手动关闭，否则持续更新。

如用户手动熄灯，设备**仍应继续 BLE 扫描，但不输出光**；
再次短按恢复时立即展示当前有效状态。

### 8.1 功能测试清单

| 编号 | 测试 | 预期结果 |
|---|---|---|
| F01 | 灯端开机，无佩戴端 | 进入等待/失联低亮状态，不高频闪烁 |

### 8.2 无网络测试

必须在以下条件下通过核心功能测试：**路由器关闭；Wi-Fi 未配置；手机飞行模式或不在场；
无互联网；无 HomeAssistant 主机**。

预期：**佩戴端广播 → 灯端显示 → 失联检测**均可正常工作。

### 8.3 距离与环境测试（普通住宅）

| 场景 | 最低预期 |
|---|---|
| 同一房间，**3–5 米**无遮挡 | 有效包率接近 **100 %** |
| 同一房间，**10 米** | 稳定更新，不频繁 `Lost` |
| 隔一堵普通室内墙 | 仍能维持合理更新；若不行应记录 **RSSI** 和丢包率 |
| 宠物蜷卧、人体遮挡 | 不应立即误判 `Lost` |
| 多个蓝牙设备环境 | 不应被非目标设备触发 |

### 8.4 长时间稳定性测试

* 连续运行：至少 **72 小时**；
* 状态切换循环：至少 **500 次**；
* 失联/恢复循环：至少 **100 次**；
* 灯端温升：`Quiet`、`Light`、`Active` 各至少运行 **2 小时**；
* 断电恢复：至少 **50 次**；
* 佩戴端模拟电池低电量：观察广播、状态与提示是否稳定。

### 8.5 可观测性日志

**开发版本 UART 日志至少输出：**

```
boot reason, firmware version, bound device id,
BLE valid packets / invalid packets / CRC errors,
last RSSI, last sequence, last_seen age,
current state, current target brightness / color,
lost transitions, restart reason
```

量产或用户体验版本应**降低日志等级**，避免串口输出影响实时性与功耗。

## 9. 关键风险与规避（第 9 节）

| 风险 | 影响 | 规避方案 |
|---|---|---|
| 购买错误灯型 | 无法套用 `bslamp2` 固件 | 购买前确认内部型号/型号；保留原厂灯对照 |
| 未备份原厂 Flash 就刷机 | 无法恢复原厂 | 首次写入前完整读取 **4 MB Flash** |
| 使用 5 V TTL | 可能损坏 ESP32 IO | 仅使用 **3.3 V** 串口逻辑 |
| TX / RX 接反或无共地 | 无法连接烧录 | TX ↔ RX 交叉，**GND 必须共地** |
| 佩戴端静止不广播 | 被灯误判为失联 | **强制心跳广播**，静止也持续发送 |
| 用 BLE MAC 作为唯一绑定 | 隐私地址变化时失效 | 使用协议内 `DeviceID` 绑定 |
| 不校验广播数据 | 被附近 BLE 或噪声误触发 | `CompanyID`、版本、长度、`CRC`、`DeviceID`、`Sequence` 多层校验 |
| `Lost` 状态太激烈 | 用户焦虑、影响夜间体验 | 用低亮低频呼吸；文案定义为"状态暂不可用" |
| 低亮度 PWM 抖动 | 产品感差 | 实测最小稳定亮度；**Gamma 与通道下限校准** |
| ESPHome 直接作为最终产品 | 依赖网络/平台耦合、不利于产品化 | ESPHome **仅作中间验证**；最终用 ESP-IDF 独立固件 |
| 宠物运动分类不稳 | 灯频繁变色 | 状态防抖、滞回、滑动窗口、活动状态最短保持时间 |

## 12. 最终工程原则（第 12 节）

1. **先保证本地闭环。** 宠物传感器到灯的状态更新必须不经过手机、服务器或云平台。
2. **先保证状态稳定，再优化状态精确。** 用户感受到的是灯光语言是否自然，
   而不是加速度模型是否复杂。
3. **先保证可恢复。** 所有刷机动作都以原厂 Flash 备份为前提。
4. **先保证低亮舒适。** 这是桌面氛围灯，不是报警器；夜间效果比高亮彩色更重要。
5. **先用广播，后做连接。** BLE 广播足以支撑 V1 的状态同步与失联判断，
   且对佩戴端最友好。
6. **先做一个绑定设备。** 多宠物、多房间、多灯联动在协议预留，但不进入 V1 必做范围。
7. **ESPHome 是验证工具，ESP-IDF 是产品路线。** 最终固件必须能独立执行
   BLE、状态机与灯效。
