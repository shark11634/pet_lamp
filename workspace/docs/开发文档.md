## 1. 项目概览

### 1.1 做什么

在**米家床头灯 2**（`bslamp2` / `MUE4093GL`）上实现一只"宠物活动状态灯"：

* 宠物佩戴 **Seeed XIAO nRF52840 Sense**，板载 IMU 判断活动强度，
  通过 BLE 广播出去
* 灯端**被动监听**广播，把活动状态映射成灯效
* 叠加夜间免打扰、多宠物支持、手机控制，同时**保留原厂全部用户可见功能**

### 1.2 硬件

| 角色 | 硬件 | 关键参数 |
|---|---|---|
| 灯 | 米家床头灯 2（`bslamp2`） | ESP32-WROOM-32D，4 MB Flash，12 V/1 A |
| 佩戴端 | Seeed XIAO nRF52840 **Sense** | 板载 LSM6DS3TR-C 六轴，只用加速度三轴 |

灯端 GPIO（需求 §4.2，已核实）：

| 功能 | GPIO |
|---|---|
| RGB PWM | 红 13 / 绿 14 / 蓝 5 |
| 白光 PWM | 12 |
| LED 主开关 1 / 2 | 33 / 4 |
| 面板 I²C | SDA 21 / SCL 19，中断 16 |
| 调试 UART | TX 1 / RX 3 |
| Boot | 0 |

### 1.3 三条硬约束

1. **原厂 4 MB Flash 必须已完整备份** —— 这是唯一回退手段。
   文件：仓库根目录 `bslamp2-stock-4MB.bin`（4,194,304 字节）。
2. **原厂固件是闭源二进制** —— 没有源码，无法在其上做真正的"增量开发"。
   因此"保留原厂功能"靠的是：复用社区验证过的硬件驱动 + 跑回归清单，
   而不是打补丁。
3. **工程内零 Python** —— 唯一例外是 ESPHome 组件必需的 `__init__.py`
   （PC 端代码生成，不进设备）。

### 1.4 规模

| 模块 | 行数 | 说明 |
|---|---|---|
| `core/` | ~2300 | 可移植纯 C99，被测代码 |
| `lamp_bslamp2/` | ~3400 | 方案 B：纯 ESP-IDF 绑定层 + 测试 |
| `esphome/` | ~1800 | 方案 A：外部组件 + 网页 |
| `test/` | ~1800 | 主机测试 |
| `protocol/` | ~570 | 参考实现与向量 |
| `tools/` | ~570 | 离线 CLI |
| `wearable_xiao/` | ~1000 | 佩戴端固件 |
| **合计** | **~11,400 行** | 断言 **488** 项 |

## 2. 系统架构

### 2.1 数据流

```
┌─────────────────── 佩戴端（XIAO nRF52840 Sense）───────────────────┐
│ IMU 采样 → 活动分类 → 组包 → BLE 广播                              │
│  · 只广播，不连接，不接收                                          │
│  · 1 s 间隔（需求 §3.5）                                           │
└────────────────────────────┬──────────────────────────────────────┘
                             │ Legacy Advertising, AD Type 0xFF
                             │ 16 字节 Manufacturer Specific Data
                             ▼
┌─────────────────── 灯端（bslamp2 / ESP32）────────────────────────┐
│                                                                    │
│  NimBLE / esp32_ble_tracker   被动扫描（passive，从不回应）        │
│         │ 原始 0xFF 字节                                           │
│         ▼                                                          │
│  core/pet_protocol.c          六层字段校验 + CRC-8                 │
│         │ 合法包                                                   │
│         ▼                                                          │
│  core/device_registry.c       多狗设备表 / 每狗独立计时 /          │
│         │                     最活跃者优先合并                     │
│         ▼                                                          │
│  core/night_mode.c            时间窗 / 空闲推断 / 手动豁免 / 节流   │
│         │ 状态 + 亮度上限                                          │
│         ▼                                                          │
│  core/lamp_effects.c          状态目标色 / 过渡 / 呼吸 / 提示       │
│         │ 逻辑颜色 + 层系数                                        │
│         ▼                                                          │
│  core/lamp_duty.c             全通道限流 + 占空比换算              │
│  core/lamp_gamma.c            Gamma 2.2                            │
│         │ 4 通道占空比（14 bit）                                   │
│         ▼                                                          │
│  平台层：LEDC（方案 B）或 light 组件（方案 A）                     │
└────────────────────────────────────────────────────────────────────┘
```

### 2.2 唯一的分层原则

**业务逻辑与硬件、与框架完全解耦。**

```
core/          纯 C99。不 include ESP-IDF / ESPHome / Arduino 头文件
   │  只通过两个回调与平台交互
   ├── lamp_output_fn      （逻辑颜色 + 层系数 + floor）
   └── lamp_pwm_write_fn   （4 通道占空比）
   │
   ├──► ESPHome 外部组件（方案 A 主线）
   └──► ESP-IDF 绑定层（方案 B / 参考实现）
```

**收益（这是本项目最重要的工程决策）**：

* 全部核心逻辑可以在 PC 上编译运行 → **488 项断言无需硬件即可执行**
* 本工程靠这一点在**没有 ESP32、没有 ESP-IDF 工具链、没有 ESPHome 的机器上**
  抓到并修掉了 10 个真实缺陷（见 §9）
* 平台切换只换薄适配层，核心零改动

**约束验证方式**（应作为 CI 的第一条）：

```powershell
gcc -std=c99 -Wall -Wextra -Wpedantic -I core -c core/*.c
```

只要 `core/` 里出现平台头文件，这条命令立刻失败。

### 2.3 决策摘要

16 项决策的完整理由见 [`docs/最终可执行方案.md`](docs/最终可执行方案.md) §1。
最影响代码形态的几条：

| 编号 | 决策 | 代码落点 |
|---|---|---|
| D1 | ESPHome 外部组件为交付基线 | `esphome/` |
| D2 | 可移植纯 C99 核心保证方案 B 能力 | `core/` |
| D3 | Python 仅限组件 `__init__.py` | 全工程仅 1 个 `.py` |
| D6 | 设备表默认 8，网页可配 1–16 | `pet_config.h` `PET_DEV_MAX_*` |
| D7 | 多狗**最活跃者优先** | `pet_reg_merge()` |
| D10 | 手动模式**暂停自动灯效**，超时自动回落 | `pet_night_*` + `lamp_fx_input_t.manual_mode` |
| D14 | 夜间 Active 上限 **18/255 ≈ 7%** | `NIGHT_CAP_ACTIVE` |

## 4. 可移植核心库 `core/`

### 4.1 唯一配置事实来源：`pet_config.h`

**所有行为参数都在这里**，`main/app_config.h` 只放平台常量
（GPIO、LEDC 通道、任务栈、NVS 命名空间）。

改行为的正确姿势：

```
改 core/pet_config.h  →  跑 test/run_all_host_tests.ps1  →  通过即完成
```

绝不要在平台层复制一份阈值。

### 4.2 模块职责

| 模块 | 职责 | 关键 API |
|---|---|---|
| `pet_protocol` | 广播字节 → `pet_packet_t`；CRC-8/ATM | `pet_parse_mfg_data()`、`pet_build_mfg_data()`、`pet_crc8()` |
| `device_registry` | 多狗表、每狗独立计时、序号回绕、合并 | `pet_reg_on_packet()`、`pet_reg_merge()`、`pet_reg_display_name()` |
| `night_mode` | 时间窗、空闲推断、手动豁免、Active 节流 | `pet_night_tick()`、`pet_night_cap_for()`、`pet_night_on_user_action()` |
| `lamp_effects` | 状态目标色、过渡、呼吸、低电提示、恢复动画 | `lamp_effects_tick()`、`lamp_effects_set_output()` |
| `lamp_duty` | 全通道限流、占空比换算（纯函数） | `lamp_compute_duty()`、`lamp_apply_current_limit()` |
| `lamp_gamma` | Gamma 2.2 查表、平台位数换算（纯函数） | `lamp_gamma_duty()`、`lamp_duty_to_bits()` |
| `lamp_driver` | 有状态封装（持有平台回调与最近占空比） | `lamp_driver_init()`、`lamp_driver_set_layer()` |

### 4.3 两个回调：`core` 与平台的唯一接触面

```c
/* 灯效层算完 → 交给平台 */
typedef void (*lamp_output_fn)(const lamp_color_t *color, float layer,
                               uint16_t floor_duty, void *user);

/* 驱动层算完占空比 → 交给硬件 */
typedef void (*lamp_pwm_write_fn)(const uint16_t *duty, void *user);
```

**踩过的坑**：这两个回调的 `user` 指针必须指向**平台层真正持有的那个**
`lamp_driver_t` 实例。本项目在写集成测试时把 `user` 传成 `NULL`，
导致 LEDC 替身永远读 0——4 个用例"合理地"失败，看起来像产品缺陷，
其实是测试接错了线。详见 §9 缺陷 #11。

### 4.4 状态与颜色的定义

```c
/* 广播里的活动状态（佩戴端产生） */
PET_STATE_QUIET = 0, PET_STATE_LIGHT = 1, PET_STATE_ACTIVE = 2

/* 灯端本地显示状态（Lost / Boot 不出现在广播里） */
PET_LAMP_BOOT, PET_LAMP_QUIET, PET_LAMP_LIGHT, PET_LAMP_ACTIVE, PET_LAMP_LOST
```

亮度区间（需求 §4.4）：

| 状态 | 目标亮度 | 偏色 | 夜间上限 |
|---|---|---|---|
| Quiet | 2%–8% | 暖白 | 10 |
| Light | 8%–20% | 青绿 | 14 |
| Active | 20%–40% | 蓝 | **18 ≈ 7%** |
| Lost | 2%–6% | 暗紫 | 6 |

> Quiet / Lost 的**实测**下限会高于标称值（约 4%–6%），原因是
> `LAMP_MIN_DUTY_LEVELS` 为保证低亮呼吸可辨识而抬高主导通道的占空比档位。
> 这是需求 §4.5 明确允许的取舍（"提高最小稳定亮度，而不是无限压低 PWM"）。
> 集成测试里断言的是**物理约束下的期望值**，注释写明了原因。

### 4.5 关键实现细节（改动前务必读）

**Q8 定点平滑**：灯效过渡用 `lamp_color_q8_t`（每通道 8 位小数）。
原因见 §9 缺陷 #4——用 8 位整数做平滑，每帧增量会被取整抹掉，
低亮呼吸直接消失。

**占空比分辨率 14 bit**：`LAMP_PWM_RES_BITS = 14`。
12 bit 时 1 LSB 在 2% 亮度下相当于 12%–25% 跳变，呼吸会变成一格一格跳。

**`floor_duty` 只用于"整体最低亮度"**，不能用来保住低亮呼吸——
那会把本来就该熄灭的通道（g/b/w = 0）一起抬起来，造成漏色。

**层乘法必须四舍五入**，且 `base > 0 && layer > 0` 时保留最小非零值。

## 5. 灯端：两条交付路线

两条路线**共享 `core/`，只换平台层**。

### 5.1 方案 A：ESPHome 外部组件（主线）

**为什么选它**：灯板与触控面板的硬件驱动（4 路 PWM + 主开关时序、
面板 I²C 协议、12 颗指示灯）复杂度高且容易烧板子，社区项目
`esphome-xiaomi_bslamp2` 已经过量产验证。ESPHome 还自带 Wi-Fi / OTA /
API / MQTT / 时间同步。

**组件设计要点**：

| 要点 | 做法 | 理由 |
|---|---|---|
| 网页不依赖 ESPHome API | `__init__.py` 把 `pet_ui.html` 生成为 C++ 原始字符串头文件；HTTP 直接用 ESP-IDF `esp_http_server` | ESPHome `web_server` 内部 API 逐版本变化，硬接会脆 |
| 不直接创建 ESPHome 实体 | 通过公开 getter 暴露，YAML 用 `lambda:` 映射 | 实体基类头文件路径会变；也把实体定义留给用户 |
| `core/` 如何进构建 | `__init__.py` 复制到 `src/pet_core/` 并加 `-I` | 平台构建只编译 `src/`；避免在工程里放重复副本 |

**网页三个页签**：

* **宠物状态** —— 合并状态、来源狗、活动分数、夜间模式、豁免剩余；
  狗狗列表（名字可改 / 状态 / 分数 / 电量 / 信号 / 最近心跳 / 只看 / 解绑）；
  进入配对、合并显示、清空绑定
* **灯光控制** —— 开关、模式（日光/彩光）、亮度 1–100、色温 1700–6500 K、颜色
  （属性模型**对齐原厂米家**）
* **设置** —— 夜间开关与时间窗、四档夜间上限、豁免时长 1–120 分钟、
  夜间节流、失联超时、设备表容量 1–16

**MQTT / HA**：`pet-lamp.yaml` 末尾给了实体映射示例（`text_sensor` /
`sensor` / `binary_sensor` / `button` 用 lambda 读 getter），配合 ESPHome
的 `mqtt:` 段由 ESPHome 自己完成自动发现。

**端口约定**：内置网页默认 **8080**，避免和 ESPHome `web_server`（默认 80）冲突。

### 5.2 方案 B：纯 ESP-IDF（参考实现）

**定位**：验证 `core/` 可移植性 + 演示如何接入 ESP-IDF + 作为 `touch_panel`
等硬件绑定的参考。`README_现状说明.md` 有完整说明。

**三档任务节奏**（需求 §6.3）：

| 任务 | 频率 | 职责 |
|---|---|---|
| `ble_rx_task` | 事件驱动 | 出队原始广播 → 协议解析 → 设备表 |
| `state_task` | 1 Hz | 夜间 tick、合并、失联、NVS（仅变化时写） |
| `fx_task` | 50 Hz | 灯效插值 + 输出 LEDC |

**为什么三个任务而不是一个大循环**：灯效必须 20–100 Hz 稳定更新，
而协议解析与 NVS 写入耗时不可预测；混在一起会出现"写一次 Flash 灯闪一下"。

#### ★ LEDC 分辨率与频率是耦合的（本项目改过两次的地方）

ESP32 LEDC：`f = 80 MHz / (2^bits × div)`，**整数分频 div ∈ [1, 1024]**。
代入 `div = 1` 得到位数下的最高可达频率：

| 分辨率 | 最高频率 | 最低频率 | 3 kHz | 10 kHz | 20 kHz |
|---|---|---|---|---|---|
| 10 bit | 78.1 kHz | 76 Hz | ✔ | ✔ | ✔ |
| 12 bit | 19.5 kHz | 19 Hz | ✔ | ✔ | ✘ |
| 13 bit | **9.77 kHz** | 9.5 Hz | ✔ | ✘ | ✘ |
| 14 bit | **4.88 kHz** | 4.8 Hz | ✔ | ✘ | ✘ |

**ESP-IDF 在分频 < 1 时会直接报
`Can not find a proper pre-divider number base on the given frequency and the current duty_resolution`**
（见 [LED PWM 控制器文档](https://docs.espressif.com/projects/esp-idf/zh_CN/v5.1.4/esp32/api-reference/peripherals/ledc.html)）。

于是本工程的最终配置是**按通道不同分辨率**：

| 通道 | 频率 | 分辨率 | 取舍 |
|---|---|---|---|
| RGB（红0/绿1/蓝2） | 3000 Hz | **14 bit** | 3 kHz 在 14 bit 可行（div 只能取 2 → 实际约 2441 Hz）。14 bit 是低亮呼吸的必要条件 |
| 白光（ch4） | **9765 Hz** | **13 bit** | 14 bit 上限只有 4882 Hz，够不到 10 kHz。9765 Hz 是 13 bit 的上限，与原厂 10 kHz 差 2.35%，肉眼看色温无法分辨 |

白光的 14→13 bit 折算用一次右移（先钳位再移位）。core 的占空比与亮度单调对应，
所以只是量化更粗一档；集成测试里有"非零不得被抹成零"的断言守着低亮地板。

**两处历史错误（都已修正，都值得记）**：

1. 最初写"20 kHz 下 ESP32 LEDC 支持 14 bit，正好够低亮呼吸"——**这是错的**。
   14 bit 上限只有 4882 Hz，20 kHz 在 14 bit 下根本不可能。
2. 改成上游频率后，`app_config.h` 里写"10 kHz @ 14 bit 依赖 IDF 小数分频"
   ——**也是错的**，ESP-IDF 不用小数分频，会直接报错。

现在这两类错误都由**编译期静态断言**拦住（见下），不再靠注释提醒。

#### 编译期守卫（替代注释）

`app_config.h` 里有：

```c
#define LAMP_LEDC_FMAX_FOR_BITS(bits)   /* 上表 */
typedef char lamp_ledc_rgb_ok[
    (LAMP_LEDC_FREQ_RGB <= LAMP_LEDC_FMAX_FOR_BITS(LAMP_LEDC_BITS_RGB)) ? 1 : -1];
```

## 7. 通信协议

完整规范见 [`protocol/README.md`](protocol/README.md)。这里只留速查。

### 7.1 帧格式

```
BLE Legacy Advertising，AD Type 0xFF
  [len=17][0xFF] + Manufacturer Specific Data

MFG 数据 16 字节 = CompanyID(2) + Payload(14)

Payload（小端序）：
  0      ProtocolVersion   0x01
  1..4   DeviceID          每只唯一
  5..6   Sequence          16-bit 递增，回绕后回 0
  7      ActivityState     0=Quiet 1=Light 2=Active
  8      ActivityScore     0–255
  9      BatteryPercent    0–100
  10     Flags             bit0 WORN / 1 CHARGING / 2 SENSOR_ERROR
                           bit3 PAIR_REQUEST / 4 LOW_BATTERY
  11..12 Reserved
  13     CRC-8/ATM         poly 0x07 init 0x00，覆盖 Payload[0..12]
```

### 7.2 测试向量

```
TV-1  FF FF 01 78 56 34 12 00 00 00 00 64 11 00 00 C8
TV-2  FF FF 01 78 56 34 12 2A 01 02 C8 55 01 00 00 CE
TV-3  FF FF 01 78 56 34 12 10 00 00 00 0E 11 00 00 36
TV-4  全零 ⇒ CRC 0x00
```

向量**唯一定义处**是 `protocol/pet_vectors.c`，它同时是独立参考实现，
会与固件实现（`core/pet_protocol.c`）交叉验证。

### 7.3 ★ "连接"到底是什么

这是最容易被误解的一点：

> **灯端与佩戴端之间没有连接。**

* 佩戴端只广播，**从不接收**
* 灯端只被动扫描（`passive=1`），**从不回应**
* 所谓"连上了"= 灯端在 `last_seen` 超时（默认 60 s）内收到过该 `DeviceID`
  的合法包

**首次"配对"也只是灯单方面记下 `DeviceID` 并写 NVS**，佩戴端毫不知情。
流程：长按面板 5 s → 60 s 配对窗口 → 接受第一个带 `PAIR_REQUEST` 的合法包
→ 暖白闪一下确认。

### 7.4 为什么这个设计是好的

* 佩戴端可以一直广播，不需要知道灯在不在 → 省电、简单、无配对状态机
* 灯端重启后自己恢复监听，不需要重连
* 代价：没有确认机制，CRC-8 **不能防伪造**（V1.1 才做截断 HMAC）

### 9.4 从缺陷清单能学到什么

**5 类反复出现的模式**：

1. **量化与取整**（#2 #4 #7 #8）——低亮度下每级变化远小于 1 个 LSB，
   整数运算会把波形吃成常数。解法：Q8 定点 + 提高 PWM 分辨率 +
   保证非零不被抹成零。
2. **顺序错误**（#2 #9 #15）——判定写在赋值前后、钳位写在移位之后，
   都是最隐蔽的一类。**凡是有"先 A 后 B"的地方，都值得问一句顺序对不对。**
3. **双重施加**（#4）——同一个降亮系数被施加两次。
4. **别名与编译器假设**（#6）——`const` 指针和可写指针指向同一对象。
5. **参数抄错一格 / 物理约束算错**（#10 #12 #13 #14）——
   `0x0C00` 看成 `0x1800`；"20 kHz 下 14 bit 可行"这种**凭感觉的硬件断言**。
   **机械比对优于肉眼；公式算一遍优于凭印象。**

**因此本项目形成四条工程习惯**：

* 低亮路径的任何改动都必须有"峰谷比"断言（不是只看亮度非零）
* 位常量与上游对照时，用脚本/校验提取而不是手抄
* 集成测试要验证"接线"，不能只验证"模块"
* **硬件约束要写成编译期断言，不要只写在注释里** ——
  #13 #14 两条错误都是"注释里写着、没人验算"造成的，
  现在由 `app_config.h` 的静态断言拦住

| LEDC | 各通道占空比 / GPIO / 定时器 / 频率 | `host_ledc_duty()`、`host_ledc_gpio()`、`host_ledc_timer_freq()` |
| 日志 | 默认静默；`-DHOST_TEST_VERBOSE_LOG` 输出到 stderr | — |

`mock_driver.{h,c}` 是"直通"驱动替身：把灯效输出直接接到适配层的写回调，
中间不经过任何 `lamp_driver_t` 实例，因此**接线正确性一测即知**。

> 注意：`mock_driver.c` 与 `core/lamp_driver.c` 同名符号，构建时
> **不要同时链接**。Gamma / 限流用的是 `core/lamp_gamma.c` 与
> `core/lamp_duty.c` 的**真实实现**。

## 13. 可观测性与验收

### 13.1 诊断日志

`diagnostics.c` 输出格式刻意做成**一行一个字段组**且前缀稳定，
`pet_tool log` 能直接解析：

```
I (12345) diag: DIAG valid=812 dup=17 unbound=3 ad=1043 mfg=845 \
                crc=0 ver=0 len=2 rssi=-63 seq=515 age=ms \
                state=Active src=merge caps=8 lost=1 night=Night
I (12346) diag: DIAG_AGE ms=412
I (12347) diag: DIAG_DEV name="旺财" id=0x12345678 battery=85 flags=0x01 \
                packets=812 resync=0
```

| 字段 | 含义 |
|---|---|
| `valid` / `dup` / `unbound` | 有效包 / 序号重复丢弃 / 未绑定丢弃 |
| `ad` / `mfg` | AD 层收到的广播数 / 含 0xFF 的条数 |
| `crc` / `ver` / `len` | 各类解析失败计数 |
| `rssi` / `seq` / `age` | 信号强度 / 序号 / 距最后心跳 |
| `state` / `src` / `caps` / `lost` | 合并状态 / 来源 / 容量 / Lost 转换次数 |
| `night` | `Off` / `Day` / `Night` / `Manual` |

低频事件用独立前缀：`BOOT`、`PAIRING start/end`。

### 13.2 有效包率验收（需求 §8.3）

ESP32 单射频，Wi-Fi 与 BLE 共存必然掉包。验收方法：

```powershell

```

看 `valid` 相对 `ad` 的比例。若掉包明显，把共存偏好从 `PREFER_BALANCE`
改成 `PREFER_BLE`（YAML 里改一个数字）。

## 15. 开发约定

### 15.1 代码

* **`core/` 不得 include 平台头文件**。用 §2.2 的命令随时验证。
* **行为参数只写在 `core/pet_config.h`**。平台层只放 GPIO / 外设参数。
* **不要在平台层复制业务数学**。本项目为此专门拆过文件
  （`lamp_gamma.c`、`lamp_duty.c`），就是为了让测试能用真实实现。
* **每个取舍都要写注释说明原因**。本项目多处注释是"别改回去，因为……"，
  这类注释的价值在半年后才会体现。
* 语言：C99（`core/`）、C++（ESPHome 组件、Arduino）、
  Python 仅限 `__init__.py`。

### 15.2 Windows / PowerShell 的三个坑（本项目都踩过）

1. **`.ps1` 文件必须带 UTF-8 BOM**，否则中文注释会导致解析错误。
2. **执行策略阻止直接运行**，必须：
   ```powershell
   powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\script.ps1
   ```
3. **绝不要用 PowerShell 的 `Get-Content` / `Set-Content` 改写含中文的源文件**
   —— 会变成乱码，或插入字面量 `` `n ``（反引号+n）而不是换行符。
   本项目因此在 `CMakeLists.txt` 里插进过字面量 `` `n ``。
   改用编辑工具或 `[System.IO.File]::WriteAllText()`。

### 15.3 若本机网络受限

本项目环境的实测可达性（供参考）：

| 目标 | 可达 |
|---|---|
| `api.github.com` | ✅（通过 web_fetch） |
| `pypi.org` / `files.pythonhosted.org` | ✅ |
| `github.com`（git clone） | ❌ 传输重置 / TLS 凭据错误 |
| `raw.githubusercontent.com` | ❌ |
| `cdn.jsdelivr.net`、`r.jina.ai` | ❌ |

**取 GitHub 文件的有效方法**：用 contents API 拿 base64 的 `content`
字段，解码后**按 git blob SHA-1 校验**。不要手工抄 base64——本项目试过，
手工转录立刻引入拼写错误。
