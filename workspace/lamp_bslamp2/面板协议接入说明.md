# 触摸面板协议接入说明

**结论：面板协议已接入并通过单元测试。** 本文记录它从哪里来、怎么验证、
真机上还需要做什么。

---

## 1. 为什么这不是"逆向"，而是"移植"

需求 §5.6 允许在阶段 A 用社区实现验证外设。面板 I²C 协议**已经有可用的
社区实现**，不需要从零逆向——那既慢又容易猜错时序把面板 MCU 写进异常状态。

采用的上游项目：

| 项 | 值 |
|---|---|
| 仓库 | <https://github.com/mmakaay/esphome-xiaomi_bslamp2> |
| 分支 | `dev` |
| 关键文件 | `components/xiaomi_bslamp2/front_panel_hal.h`（346 行，blob SHA `9fdc26de…90106`） |
| 硬件参数出处 | `packages/core.yaml`（blob SHA `0e284779…14efc8`） |

上游文件已取回并留存在 `lamp_bslamp2/_panel_ref/`，**内容按 git blob SHA-1
逐字节校验**（不是手抄的 base64）。移植时保留出处与许可证声明
（见 `main/panel_protocol.h` 文件头）。

### 核实的硬件参数（全部来自 `packages/core.yaml` 原文）

```yaml
i2c:
  id: front_panel_i2c
  sda: GPIO21
  scl: GPIO19
  scan: true
xiaomi_bslamp2:
  front_panel:
    i2c: front_panel_i2c
    address: 0x2C        # ← 面板从机地址
    trigger_pin: GPIO16  # ← 中断脚，下降沿
```

这与本工程从需求 PDF 恢复的引脚表**完全一致**。

## 2. 协议摘要

7 字节定长消息。读事件 = 先写 `READY_FOR_EV` 再读 7 字节。

```
事件消息：
  m[0..3] = 04 04 01 00            固定前缀
  m[4]    = 部位  01 电源键 / 02 色彩键 / 03 滑条触摸 / 04 滑条松开
  m[5]    = 类型码  或  滑条原始值
  m[6]    = 校验   按键: 类型码 + m[4]
                   滑条: m[5] + m[4] + 1

按键：m[5]=01 且 m[6]=02+m[4] → 触摸
      m[5]=02 且 m[6]=03+m[4] → 松开
滑条：m[5] 必须 01..16（1..22），档位 = 23 − m[5]

写指示灯：
  {02, 03, state>>8, state&0xFF, 64, 00, 00}
  state 15 bit：bit14 电源灯 / bit12 色彩灯 / bit9..0 滑条 10 颗灯
  固定位 0x0C00 恒被写入（上游 turn_on/off_leds 按位或）
```

事件码位域（与上游逐位一致，便于对照）：

| 位 | 含义 |
|---|---|
| 0 | OK |
| 1–3 | 部位 |
| 4–5 | 类型（1 触摸 / 2 松开） |
| 6–10 | 滑条档位 0–22 |

## 3. 代码结构

```
main/panel_protocol.h/.c    纯函数：解析 7 字节 + 编码 LED 消息
                            ← 无任何硬件访问，因此可以穷举测试
main/touch_panel.h/.c       I²C 总线、中断（GPIO16 下降沿）、事务、事件翻译
test/host_panel_test.c      97 项断言
```

**分层理由**：协议正确性不依赖真机。真机只需验证"电气与接线"，
这大幅缩小了上机后才可能踩的坑。

## 4. 移植时抓到的一个真实错误（值得记下来）

`turn_on_leds()` 里有一个固定常量 `0b0000110000000000`。

我第一次读成 `0x1800`（bit12+bit11/12），**正确值是 `0x0C00`**（bit11+bit12 的
另一种读法）。差别是一个 bit，后果是**电源灯位写错**。

修正后加了两条回归断言把它钉死：

```c
t_eq(PANEL_LED_TX_BITS, 0x0C00u, "固定位 = 0x0C00（上游 0b0000110000000000）");
t_check((PANEL_LED_TX_BITS & 0x2000u) == 0u,
        "固定位不含 bit13（防止把 0x0C00 写成 0x1800）");
```

这就是把上游文件按 SHA 取回来做机械比对的价值——肉眼读位串很容易错一格。

## 5. 顺带核实的两处"功能等价"偏差（已修正）

对照上游 `packages/core.yaml` 时发现本工程的灯板参数与上游不同，已改齐：

| 项 | 上游（原厂行为） | 本工程原值 | 现状 |
|---|---|---|---|
| RGB 载波频率 | **3000 Hz** | 20 kHz | 3 kHz（14 bit，div 只能取 2 → 实际约 2441 Hz） |
| 白光载波频率 | **10000 Hz** | 20 kHz | **9765 Hz**（13 bit 的上限；14 bit 只有 4882 Hz，够不到 10 kHz） |
| 白色 LEDC 通道 | **ch4** | ch3 | 已改为 ch4 |
| 定时器数量 | 2（RGB / 白光分开） | 1 | 已改为 2 |
| 各通道分辨率 | 未声明（ESPHome 自选） | 统一 14 bit | RGB 14 bit / 白光 **13 bit** |

> **两处曾经写错、现已由编译期断言拦住的事实**：
> ① "20 kHz 下 ESP32 LEDC 支持 14 bit" —— 错的，14 bit 上限只有 4882 Hz；
> ② "10 kHz @14 bit 靠 IDF 小数分频" —— 也是错的，ESP-IDF 在分频 < 1 时
> 直接报 Can not find a proper pre-divider。
> 详见 docs/开发文档.md §5.2 与缺陷 #13 / #14。

**为什么频率重要**：RGB 灯板是恒流驱动，频率影响开关损耗与有效导通时间，
因此会改变实际亮度与色温。本工程原本选 20 kHz 是为了避开可闻噪声，但
上游已在量产中验证 3 kHz 不啸叫。"与原厂用户可见功能等价"包含颜色输出等价，
所以采用原厂参数而不是更漂亮的数字。

## 6. 真机上还需要做的事

代码已就绪，但真机验证无法在 PC 上完成。上机后按下面顺序确认：

1. **看启动日志**：应出现
   `面板在线：地址 0x2C，中断 GPIO16，I²C 100000 Hz`
   若出现 `面板在 0x2C 无应答`，会自动扫一次总线并打印所有应答地址
   —— 若实际地址不是 0x2C，改 `touch_panel.c` 顶部的 `PANEL_I2C_ADDR`。
2. **按一下电源键**：日志应出现 `面板事件：电源键`。没有事件时看
   `touch_panel_irq_count()`（诊断日志里可加）：计数不涨说明中断线没接好，
   此时驱动会退化为约 400 ms 的周期轮询（仍能工作，只是延迟略大）。
3. **滑条**：只有**松开**时上报一次亮度（避免拖动过程中反复写 NVS）。
4. **面板灯**：当前用于显示"当前焦点是第几只狗"——
   合并显示时按在册狗数点亮滑条灯，单只时额外点亮色彩灯。
   若极性反了（亮的颗数不对），检查 `panel_slider_leds_for_ratio()` 的阈值。
5. **走一遍原厂功能回归 P01–P21**（`docs/最终可执行方案.md` §9），
   结果填进 `docs/验收测试记录模板.md`。这是"用户可见功能等价"的最终判据。

### 已知无法在 PC 上验证的部分

* I²C 时序本身（100 kHz、NACK 行为）——只能真机确认
* 面板 MCU 对连续写入 LED 状态的接受度（当前实现已做"仅变化时写"的保护）
* 中断极性（`GPIO_INTR_NEGEDGE`）——上游注释是"拉低一小段时间"，与之一致
